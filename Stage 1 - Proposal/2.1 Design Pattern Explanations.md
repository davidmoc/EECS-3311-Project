
The system uses six design patterns: **MVC, Facade, Command, Factory Method, Adapter, and Observer**. These patterns are used to solve specific design problems within the application rather than simply to satisfy the numerical requirement. This is consistent with the Stage 1 instructions, which require at least five meaningful patterns and, for each pattern, an explanation of the problem addressed, participating classes, class roles, rationale, and consequences of not using the pattern. 

### **1. MVC — Model-View-Controller**

**Design Problem Addressed:**  
The application provides several user-facing interfaces, including news browsing, research, document reading, library search, saved workspaces, and reader-profile management. The presentation logic for these interfaces should remain separate from application and domain logic. Otherwise, UI components could become responsible for research execution, database access, personalization, and other unrelated responsibilities.

**Participating Classes:**

- **Views:** `NewsView`, `ResearchView`, `ReaderView`, `LibraryView`, `WorkspaceView`, `ProfileView`
- **Controllers:** `NewsController`, `ResearchController`, `ReadingController`, `LibraryController`, `WorkspaceController`, `ProfileController`
- **Model/Application Components:** domain objects and services such as `Event`, `Document`, `ResearchResult`, `ReaderProfile`, `NewsService`, `LibraryService`, and `PoliticalResearchAgent`

**Roles of Participating Classes:**  
The View classes display information and collect user input. Controller classes receive actions from the views and coordinate the appropriate application services. Domain objects and services contain the actual state and behavior of the application.

For example, `ResearchView` collects a research request and forwards it to `ResearchController`. The controller delegates the task to `PoliticalResearchAgent` rather than performing research directly.

**Why the Pattern Is Appropriate:**  
The application contains multiple complex GUI views as well as a CLI. Separating presentation from application logic allows the same underlying functionality to be accessed through different interfaces without duplicating the research, reading, or personalization logic.

**Without MVC:**  
UI classes would likely become tightly coupled to services, repositories, and AI components. Supporting both GUI and CLI interaction would require duplicated logic, and changes to the user interface could unintentionally affect core application behavior.

### **2. Facade**

**Design Problem Addressed:**  
Executing a research request involves many internal components, including `ResearchPlanner`, `DialecticalMaterialistResearchMethod`, `ConcreteSituationBuilder`, `ToolManager`, `LLMClient`, `ResearchStoppingPolicy`, persistence, and personalization. Controllers should not need to understand or coordinate all of these components themselves.

**Participating Classes:**

- `PoliticalResearchAgent` — Facade
- `ResearchPlanner`
- `DialecticalMaterialistResearchMethod`
- `ConcreteSituationBuilder`
- `ToolManager`
- `LLMClient`
- `ResearchStoppingPolicy`
- `ResearchRepository`
- `ReaderProfileService`

**Roles of Participating Classes:**  
`PoliticalResearchAgent` provides a simplified interface to the research subsystem through operations such as:

`research(request)`  
`answerQuestion(question)`  
`continueResearch(sessionId, request)`

Internally, the facade creates or restores a research session, requests an initial plan, executes research steps, updates the evolving `ConcreteSituation`, evaluates whether additional research is necessary, and eventually produces a `ResearchResult`.

The other participating classes perform specialized work but are hidden behind the facade from callers such as `ResearchController`.

**Why the Pattern Is Appropriate:**  
The research subsystem is intentionally complex because it performs iterative agent behavior rather than one LLM request. A facade gives the rest of the application a simple way to use this subsystem without becoming dependent on its internal structure.

**Without Facade:**  
`ResearchController` and other callers would need direct knowledge of planning, LLM interaction, research commands, tool execution, evidence evaluation, stopping conditions, persistence, and personalization. This would produce high coupling and make future changes to the research architecture much more difficult.

### **3. Command**

**Design Problem Addressed:**  
Research is not executed as one fixed operation. The agent constructs a plan containing multiple research actions and can revise that plan as new evidence, contradictions, historical questions, or missing relationships are discovered. These actions require a common representation so that they can be scheduled and executed dynamically.

**Participating Classes:**

- `ResearchCommand` — Command interface
- `RetrieveEvidenceCommand`
- `InvestigateRelationCommand`
- `TraceHistoricalDevelopmentCommand`
- `InvestigateContradictionCommand`
- `TestExplanationCommand`
- `RetrieveTheoryCommand`
- `CompareSourcesCommand`
- `SynthesizeResearchCommand`
- `ResearchPlan` — stores and schedules commands
- `ResearchPlanner` — creates and revises command sequences
- `PoliticalResearchAgent` — orchestrates execution

**Roles of Participating Classes:**  
`ResearchCommand` defines a common `execute()` operation. Each concrete command encapsulates one kind of research task. `ResearchPlan` contains one or more commands, while `ResearchPlanner` determines which commands are needed.

For example, after initial evidence retrieval, the system may discover that an important historical relationship is poorly understood. The planner can add a `TraceHistoricalDevelopmentCommand`. If conflicting evidence is found later, it can introduce a `TestExplanationCommand`.

**Why the Pattern Is Appropriate:**  
The Command pattern fits the iterative nature of the research agent because research actions must be represented as objects that can be created, stored, ordered, replaced, executed, and potentially retried.

It also allows the dialectical-materialist research process to affect the execution plan dynamically rather than requiring a rigid sequence established before research begins.

**Without Command:**  
Research behavior would likely become a large sequence of conditional statements inside `PoliticalResearchAgent` or `ResearchPlanner`. Adding a new type of research operation would require modifying central orchestration logic, and dynamically revising a research plan would be significantly more complicated.

### **4. Factory Method**

**Design Problem Addressed:**  
The agent can use several different tools, including news search, general web search, library search, historical-source retrieval, and theory retrieval. Components that need a tool should not have to know how every concrete tool is constructed.

**Participating Classes:**

- `ToolFactory` — Creator
- `Tool` — Product interface
- `NewsSearchTool`
- `WebSearchTool`
- `LibrarySearchTool`
- `HistoricalSourceTool`
- `TheorySearchTool`
- `ToolManager`

**Roles of Participating Classes:**  
`Tool` defines the common operations that agent tools must support, such as `validate()` and `execute()`.

The concrete tool classes implement specific capabilities.

`ToolFactory.createTool(type)` determines which concrete implementation should be created for a requested tool type. `ToolManager` manages and invokes the resulting tools.

**Why the Pattern Is Appropriate:**  
The agent’s available tools may expand during implementation. Factory-based construction allows new tools to be introduced while keeping their creation separate from the components that use them.

For example, adding a new academic-paper retrieval tool should not require `PoliticalResearchAgent` to know how that tool is initialized.

**Without Factory Method:**  
Tool creation logic would be scattered throughout the application or implemented through repeated direct constructor calls and conditionals. The agent subsystem would become more tightly coupled to concrete tool implementations, making extension and testing more difficult.

### **5. Adapter**

**Design Problem Addressed:**  
The application depends on external systems that may expose incompatible APIs and data formats. For example, an external news service may return data differently from a public text archive, and an OpenAI model API has its own request and response format. Internal application components should not depend directly on these vendor-specific interfaces.

**Participating Classes:**

- `LLMClient` — internal LLM interface
- `OpenAILLMAdapter`
- `NewsProvider` — internal news-provider interface
- `ExternalNewsAPIAdapter`
- `WebProvider` — internal web-search interface
- `WebSearchAPIAdapter`
- `DocumentProvider` — internal document-provider interface
- `PublicTextArchiveAdapter`

**Roles of Participating Classes:**  
The interfaces define the operations expected by the application. Adapter classes communicate with specific external services and translate their requests and responses into the application’s internal representations.

For example, the rest of the system communicates with `LLMClient.generate()` rather than depending directly on OpenAI-specific API structures. `OpenAILLMAdapter` performs the required conversion.

Similarly, `NewsSearchTool` depends on `NewsProvider`, not on a particular news API.

**Why the Pattern Is Appropriate:**  
External APIs can change or be replaced, and the project may eventually use more than one provider. The Adapter pattern isolates those differences from the rest of the software.

It is particularly useful for this project because source retrieval is central to the product and will likely rely on several external services.

**Without Adapter:**  
Vendor-specific API structures would spread throughout the application’s business and agent logic. Replacing a news API, document archive, search provider, or LLM provider could then require modifications across many unrelated classes.

### **6. Observer**

**Design Problem Addressed:**  
The Reader Model should evolve as the user interacts with the application. Activities such as reading a text, completing material, researching a topic, or demonstrating familiarity with a concept may provide useful information for updating the user’s knowledge profile and future recommendations. However, every controller should not need to know exactly how the Reader Model is updated.

**Participating Classes:**

- `LearningEventBus` — Subject
- `ActivityObserver` — Observer interface
- `ReaderModelUpdater` — Concrete Observer
- `ReaderProfileService`
- `ReadingController`
- `ResearchController`

**Roles of Participating Classes:**  
Controllers publish relevant activity to `LearningEventBus`.

`LearningEventBus` maintains registered observers and notifies them when activity occurs.

`ReaderModelUpdater` implements `ActivityObserver` and reacts to relevant activity events. It uses `ReaderProfileService` to update the reader’s evolving profile when appropriate.

For example, completing an introductory text on a topic can publish a learning event. `ReaderModelUpdater` can use that event when updating the user’s reading history or estimated familiarity without requiring `ReadingController` to directly manipulate the Reader Model.

**Why the Pattern Is Appropriate:**  
Several independent parts of the application can produce information relevant to personalization. Observer allows those components to publish activity without being directly coupled to the components that consume it.

This is especially appropriate for an evolving Reader Model because additional observers could later be introduced for recommendations, analytics, or progress tracking without changing the components that generate the events.

**Without Observer:**  
Each controller would need explicit dependencies on `ReaderProfileService` and would need to know when and how every type of user activity should affect the Reader Model. That would spread personalization logic throughout the application and make future extensions more difficult.
